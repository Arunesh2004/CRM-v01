TESTING CONDITIONSAI Security + Business CRM PlatformAdmin → Employee → Full Workflow → Security → Communication → Credential ReadinessPurpose: a complete evidence-first testing specification for the CRM before customer credentials are requested. It defines what must be tested, how it must be tested, how positive and negative paths are handled, and what evidence is required. It is not a declaration that every capability is currently implemented or production-certified.1. Governing PrinciplesEvidence beats assumptions: code existence is not runtime proof.Test the real hosted deployment for hosted claims; distinguish code-only, automated-test, hosted, authenticated-E2E, provider-E2E and production-certified evidence.Never weaken authentication, authorization, RLS/FORCE RLS, SSRF, rate limits, webhook validation or tenant boundaries to make a test pass.Never invent provider success. Missing credentials must result in explicit demo/test behavior or safe degradation according to capability criticality.Never paste passwords, API keys, database URLs, cookies, tokens or private secrets into chat, source control, reports or logs.Use synthetic/demo data. Never alter real customer data during testing.Every PASS requires reproducible evidence. Use PASS / FAIL / BLOCKED / DEFERRED / NOT APPLICABLE.Test happy paths AND unauthorized, malformed, duplicate, stale, timeout, retry and provider-failure paths.Do not call implementation maturity production certification. The project explicitly keeps these separate. fileciteturn284file02. Architectural ContextThe current target architecture is one codebase with a separately provisioned deployment/environment/infrastructure/credential set per company. Deployment isolation is the outer boundary; tenant isolation, application authorization and PostgreSQL RLS remain security boundaries inside a deployment. External vendors belong behind provider contracts/adapters, so customer credentials should configure the deployment rather than require a rewrite of CRM business logic. fileciteturn284file4The testing program must therefore prove both the product itself and the ability to operate it safely when optional providers are missing. The current roadmap specifically identifies provider E2E, realtime/browser E2E, CCTV infrastructure, AI provider behavior, chaos/data-loss testing, DR, scale, provisioning and final certification as evidence areas that cannot be replaced by source inspection. fileciteturn284file23.
