Executive Summary This document is the detailed continuation record for the AI Security + Business CRM project as of 12 September 2026. It is intentionally more than a progress report: it explains what the product is supposed to become, how the architecture evolved, what has actually been built, what has been verified, what remains, how development should proceed when production credentials are unavailable, and how the same codebase is expected to adapt to different client infrastructure. The project is not a simple CRM. The target platform combines business CRM, communication and telephony, CCTV/security operations, AI-assisted analysis, realtime notifications, workforce/field operations, reporting, enterprise controls, background workers, observability/disaster recovery and isolated company deployments. The original vision included a conventional multi-tenant SaaS subscription model, but that commercial model was later superseded. The current commercial/deployment decision is: ONE CODEBASE → separate deployment per company/customer. A deployment may have its own application hosting, database, authentication configuration, storage, communication providers, AI provider, realtime provider, MediaMTX/worker infrastructure and secrets. Platform-level subscription checkout/payment processing is therefore not a current development blocker. Revenue management inside the CRM—products, pricing, quotations, approvals and business revenue—remains a valid product capability. The most important current strategy change is provider portability. Development must not stop because a future client has not supplied every production API credential. Where the repository supports a provider interface, development should use an explicit Demo/Test Provider so the product remains demonstrable and workflows can be completed. When the client supplies real credentials, the provider configuration is swapped without redesigning the business layer. This must never become silent fake production behavior. 2. The Deployment Model — The Most Important Current Decision The system should be treated as a deployable product package, not as a single permanent shared SaaS installation. The same source code is the product; each customer receives an isolated runtime/configuration. Target topology: ONE CODEBASE │ ├── Company A deployment → App + DB + Clerk + providers + workers + secrets ├── Company B deployment → App + DB + Clerk + providers + workers + secrets └── Company C deployment → App + DB + Clerk + providers + workers + secrets This means tenant isolation remains important inside a deployment, while deployment isolation becomes the outer security boundary between companies. A company’s credentials must never be reused by another company. The roadmap document defines the intended first-company lifecycle as: client purchase/engagement → collect requirements → provision isolated infrastructure → configure secrets → create DB/apply migrations → create company → create founding admin/head → configure Clerk → configure providers → configure domain/email → deploy workers/CCTV if required → smoke test → security test → handover. fileciteturn205file17 ADMIN_EMAIL must never become a permanent authorization bypass. Provisioning shortcuts are bootstrap mechanisms only; final authorization must be database/RBAC driven. 4. Complete Project History &amp; Architectural Evolution 5.1 Original direction The original project vision combined CRM, CCTV/AI monitoring, security operations, communications, staff/field management, reports, dashboards/mobile and business functions. The original commercial plan also assumed a traditional multi-tenant SaaS with subscriptions, trials and payment processing. The later deployment decision superseded that part of the roadmap. fileciteturn205file5 5.2 Database and Prisma fracture A major historical problem was migration/schema divergence. Orphaned C11 migration SQL was found whose intended changes did not match schema.prisma, the local physical database and/or applied migration history. The recovery direction became forensic preservation, schema reconciliation, native Prisma migration generation, and Expand → Deploy → Backfill → Contract sequencing where required. The later stabilization program strengthened this into Five-Way Database Reconciliation plus empty/disposable database migration testing. fileciteturn205file9 5.3 Application-only isolation → PostgreSQL RLS The project learned that tenantId filtering in application queries is not sufficient as the sole security boundary. Missing RLS on AI-related tables was identified as a serious historical risk. The architecture was strengthened with PostgreSQL RLS plus application-level authorization and ownership checks, followed by adversarial cross-tenant testing. fileciteturn205file12 5.4 Serverless workers → persistent external workers Early designs placed long-running processing, filesystem operations and lease heartbeats in serverless/API execution. This was rejected because Vercel functions are not persistent daemons and cannot own the filesystem of an external recording machine. The corrected topology makes Vercel responsible for UI/API/orchestration while persistent workers handle local files, long-running processing, recording ingestion and AI work. fileciteturn205file15 5.5 Fake CCTV → MediaMTX + worker architecture The early CCTV presentation was effectively a simulated stream. The project then pivoted to a real architecture: Camera → MediaMTX → authenticated webhook → durable job → node-affine worker → verified storage → AI job/event. This is a major architectural correction, not merely a UI enhancement. fileciteturn205file15 5.6 Brittle credentials → provider health/degradation Earlier providers could crash when credentials were absent and mock implementations had created a risk of fake success. The current rule is that missing credentials are a capability state. Provider states include READY, MISSING_CREDENTIALS, MISCONFIGURED and UNAVAILABLE, combined with criticality such as CRITICAL, DEGRADED and OPTIONAL. fileciteturn205file1 5.7 Realtime correction Persistent/local WebSocket assumptions were rejected for the Vercel architecture. The intended direction is a managed realtime provider with tenant/channel authorization, permission validation and controlled degradation. Candidates historically considered include Pusher, Supabase Realtime and Ably. fileciteturn205file14 6. Missing Credentials Policy — Explicit Demo Mode The intended interpretation for development is now clear: if a provider credential is not available, the project should still be made as functionally complete as possible by using an explicit Demo/Test Provider behind the same interface. The application should not be forced to wait for a future customer's credentials. This is different from secretly returning fake production results. Demo mode must be explicit, environment-controlled, visible in provider health/state, and impossible to accidentally activate as the production provider path. Scenario Required behavior Credential available and valid Use the real provider. Credential missing for optional/degraded capability Use explicit demo/test provider during development if supported; otherwise show capability as unavailable/degraded. Credential missing for critical infrastructure Do not fake success. Block/retry/quarantine affected jobs safely. Provider misconfigured Report MISCONFIGURED and fail deterministically; do not silently switch to fake production behavior. Provider temporarily unavailable Report UNAVAILABLE and use bounded retries/degradation according to capability. Production deployment Demo provider must be disabled unless the client explicitly purchased/approved a demo-only deployment. Client gives .env later Replace provider configuration/secrets; business services/UI should remain unchanged because they consume the provider interface. Critical example: object storage is not just an optional UI integration for CCTV ingestion. If storage is unavailable, the worker must not claim successful durable storage and must never delete the local recording simply because an upload was attempted. The invariant is upload success → integrity verification → durable DB state → only then local deletion. fileciteturn205file6 AI has a different criticality: if Gemini or another AI provider is absent, an AI job may be explicitly skipped/failed with a deterministic reason such as MISSING_CREDENTIALS. It must not silently generate a fake 'AI detected person/fire/etc.' result and present it as real production inference. fileciteturn205file1 9. Database Portability — Supabase Today, AWS Tomorrow The product should not be designed as if Supabase is the product itself. Supabase is one infrastructure implementation of the PostgreSQL layer. The application should depend on PostgreSQL-compatible contracts through Prisma and a small, explicit infrastructure adapter layer. Portability layer Rule ORM/domain data access Prefer Prisma/domain services rather than vendor-specific SQL. PostgreSQL RLS Keep tenant/security policies as explicit migration assets; document any platform-specific role/GUC assumptions. Extensions Track required extensions such as pgvector explicitly; validate availability on target provider. Roles Document crm_app_user/crm_system_user semantics and recreate equivalent roles safely on target PostgreSQL. Connection pooling Do not assume Supabase pooler behavior; validate direct/pooler URLs and transaction semantics on each target. Storage Do not couple database records to a specific object-storage implementation. Backups/PITR Treat backup and recovery as deployment infrastructure, not application logic. Migration process Provision a fresh target database and run the canonical migration baseline before importing client data. Provider certification AWS/Supabase/other targets each receive a compatibility smoke test before a client handover. The intended client deployment matrix therefore becomes configurable rather than hardcoded. For example: Client A could use Vercel + Supabase + Clerk + Twilio; Client B could use AWS hosting + RDS PostgreSQL + Clerk + another telephony provider; Client C could use another compatible hosting/database combination. The application layer should remain the same wherever the selected adapters and infrastructure contracts are supported. 11. Environment Variable &amp; Secret Management Rules Never store client secrets in source control. Never paste production secrets into chat, issue trackers or documents. Never print full secrets in logs or audit output. Use .env.example for variable names and descriptions, never real secret values. Classify variables as required, optional/degraded, demo/test-only or legacy/deprecated. The client’s .env belongs to that client deployment; do not reuse one company’s credentials in another. Provider selection and provider credentials must be independent of business logic. When a client moves from Supabase to AWS, change infrastructure configuration/adapters rather than rewriting CRM domain workflows. When a client provides real credentials, run provider-specific smoke tests and then production-like security tests. Rotate any credential that appeared in a transcript or other uncontrolled location. 19.
