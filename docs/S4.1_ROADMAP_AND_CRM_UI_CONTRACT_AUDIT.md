## F. Security Contract

- **Backend Authoritative**: The frontend MUST NOT implement optimistic authorization. All API calls execute via Next.js Server Actions wrapped in `withServerActionContext`, which inherently checks JWT, loads the `Tenant`, and enforces RLS in the database connection string.
- **UI Degradation**: The frontend should conditionally render buttons (e.g. `Disable "Delete" if missing DELETE permission`) for UX purposes only.
- **Tenant Boundary**: Inherently provided by `requireTenant()` and backend RLS. Frontend must simply supply the correct context or headers if necessary (usually handled via Next.js cookies).

## G. Recommended Implementation Order

1. **Global App Shell & Navigation**: Essential foundation. Includes Clerk User Button and tenant switcher.
2. **Customers & Contacts**: Basic list views, forms, and detail pages. (Lowest complexity, high value).
3. **Tasks & Activities**: Foundation for cross-entity features.
4. **Leads & Pipelines (Deals)**: Requires UI complexity (Drag and Drop / Kanban).
5. **Dashboard**: Must be built last, as it aggregates metrics from Customers, Deals, and Tasks.

*Note: Arbitrary screen order is dangerous. The dependency-aware order above ensures core objects exist before relationship-heavy views (Dashboards) are built.*
