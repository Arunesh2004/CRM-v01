## 4. Existing Components Reused
- **Primitives**: `Button`, `Input`, `Card`, `Badge`, `Tabs`, `Skeleton`, `EmptyState`
- **Shell**: The layout natively reuses the unified `CRMLayoutClient` sidebar and header.

## 5. Customer Functionality
- **List**: Renders a paginated, searchable, and filterable table of customers. Handles empty states gracefully.
- **Create**: Powered by a robust `<CustomerForm>` that validates against `CreateCustomerSchema`.
- **Detail**: The `[id]/page.tsx` route correctly resolves customer data, falling back to a global `notFound()` state if the customer ID doesn't exist or is outside the tenant context.
- **Edit**: Inline editing is supported via `<EditCustomerForm>` mapped directly to the `updateCustomerAction`.

## 6. Contact Functionality
- **List**: Contacts render dynamically inside the Customer Details `TabsContent`.
- **Create**: Powered by `<ContactForm>`, correctly scoping the creation to the current `customerId`.
- **GAP DISCOVERED (PARTIAL)**: The backend `customer.actions.ts` currently **lacks** Server Actions for `updateContactAction`, `deleteContactAction`, or `archiveContactAction`. In strict compliance with the architecture rules, I did not silently invent these backend APIs. The UI reflects this limitation by only allowing Contact creation.

## 7. Authorization Behavior
- No artificial client-side boundaries were introduced.
- All actions execute via `withServerActionContext`, wrapping the payload with strict `requireAuth()` and `requirePermission('CUSTOMER', 'READ' | 'UPDATE')` checks inside the backend service. 

## 8. Tenant Behavior
- Multi-tenant data segregation is strictly enforced by `requireTenantFromIdentity()` and `withTenantTransaction()`. 
- Conceptually verified: User A cannot edit a Customer from another tenant by manipulating the URL ID because the database `where: { id: input.id, tenantId }` predicate strictly scopes the operation in `updateCustomer()`.

## 9. Validation
- Frontend and Backend perfectly mirror the Zod definitions in `src/modules/crm/validators/customer.schema.ts`.
- Submissions wait for authoritative backend success states, ignoring pure client-side overrides.

## 10. Error / Loading / Empty States
- **Loading**: Implemented via React `<Suspense>` boundaries and Shadcn `<Skeleton>` blocks.
- **Empty State**: Handled natively using `<EmptyState>` components when no results are found.
- **Errors**: `sanitizeClientError` securely unwraps backend rejections and bubbles them to the frontend `Toaster` mechanism without exposing database internals.

## 11. Accessibility
- All inputs are associated with semantic labels.
- `lucide-react` SVGs are paired with readable text nodes.
- Full keyboard operability is inherited from the `radix-ui` primitives underpinning the Shadcn components.
