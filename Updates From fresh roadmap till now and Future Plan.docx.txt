Important Security Lessons That Changed the Product Tenant isolation cannot depend only on Prisma where clauses; PostgreSQL RLS and application authorization are defense-in-depth layers. Serverless request handlers cannot safely act as persistent CCTV filesystem workers or long-lived daemons. Recording data must follow Upload → verify object/integrity → durable DB state → delete local source only after success. Workers require node affinity, leases, fencing, stale-write rejection and controlled recovery. Webhook authenticity requires cryptographic verification, replay protection and durable idempotency. Optional providers must degrade explicitly; missing credentials must never create fake success. External provider idempotency must not be claimed merely because the CRM has an internal idempotency key. AI must never receive unrestricted database access; tool authorization belongs to the application. Production deployment success is not equivalent to production certification. Historical migration evidence must be reconciled rather than discarded merely to make a migration command look clean. 6. Current External Blockers and Credential Policy Missing external credentials are treated as integration blockers, not excuses to fabricate behavior. The credential policy distinguishes core security infrastructure from optional provider integrations. Real credentials must be used only in their intended deployment/secret store. Never print, paste, commit or document secret values. Production credentials must never be copied into local, preview, staging, demo or test environments. Optional email, SMS/voice, AI, storage, realtime and CCTV integrations may be unavailable/degraded when credentials/infrastructure are absent. Missing providers must produce explicit unavailable/degraded behavior, never fake message IDs, delivery timestamps, calls, recordings or AI detections. Buyer credentials belong only to the buyer's isolated deployment. Supported alternative providers require existing adapters or a new adapter; credentials alone do not create compatibility. Production testing remains read-only unless explicitly authorized; provider test calls must use known-safe non-Production resources. This policy is central to future development because it allows product work to continue without pretending unavailable infrastructure is operational. 8. What Will Happen When a Real Client Arrives The intended onboarding sequence is configuration and certification, not rewriting the product: CLIENT ↓ ISOLATED DEPLOYMENT ↓ DATABASE + AUTH + SECURITY ↓ CLIENT PROVIDER CREDENTIALS ↓ HEALTH / CAPABILITY CHECKS ↓ NON-DESTRUCTIVE INTEGRATION TESTS ↓ SMOKE + SECURITY CERTIFICATION ↓ READY / HANDOVER A client may use a different compatible infrastructure combination, but compatibility must be validated. For example, the source architecture permits a target such as AWS/RDS instead of Supabase when PostgreSQL, extensions, roles, pooling and required infrastructure semantics are actually compatible. It does not promise that arbitrary vendors work without adapters. 15. Authoritative Rules for Every Future Phase Read the latest handover, roadmap and repository state before changing architecture. Prefer the latest explicit architectural decision when historical documents conflict. Do not restart completed work without a new reproducible defect. Audit before implementation and define acceptance criteria first. Use the smallest complete change and add focused adversarial tests. Run relevant TypeScript, Prisma, lint and broader suites as applicable. Inspect git diff/status before completion. Use PASS/FAIL/BLOCKED/DEFERRED/ACCEPTED RISK explicitly. Never claim runtime behavior from code inspection when executable evidence is possible. Never invent credentials or provider success. Never trust client-supplied tenant/resource identifiers without authorization. Never give AI unrestricted database access. Never place persistent CCTV workers/filesystem processing in serverless routes. Never delete CCTV artifacts before verified durable storage. Never weaken tests or hide failures with blanket suppression. Keep every customer's credentials isolated to that customer's deployment. 18.
