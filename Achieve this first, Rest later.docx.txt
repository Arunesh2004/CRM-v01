Achieve this first, Rest later AI Security + Business CRM Platform Client-Demo Milestone &amp; Execution Direction Checkpoint: 16 September 2026 Purpose: define the immediate milestone required to make CRM-v01 suitable for a trustworthy client demonstration, while deliberately postponing provider-dependent and final production-certification work until the required infrastructure and credentials are legitimately available. 1. The Immediate Objective The immediate objective is NOT to finish every remaining production-certification item before the client sees the product. The immediate objective is to reach a trustworthy hosted client-demo state: the CRM's architecture and UI should be complete and synchronized for the Admin and Employee workflows; core CRM functionality should actually work; security boundaries should be sufficiently verified; and provider-dependent capabilities should exist in the product but degrade honestly when their external credentials or infrastructure are missing. The client should be able to see the product as a coherent, working CRM rather than a collection of unfinished screens. Missing credentials must affect only the provider-backed capability that depends on them. They must not be used as an excuse for unfinished core CRM functionality. 2. What 'Client-Demo Ready' Means A known hosted Vercel deployment is available and READY. Admin can sign in through the normal authentication flow. Admin can navigate the complete administrative/business workflow. Admin can create/invite an Employee through the intended lifecycle. Employee can sign in and use every page/action permitted by the assigned role. Employee is denied server-side when attempting representative Admin-only operations. Core CRM workflows are usable end-to-end. Important buttons/actions have been exercised rather than merely rendered. UI, Server Actions/APIs, database models and DTO contracts are synchronized. Loading, empty, error and permission states are truthful and usable. Provider-dependent pages remain present and architecturally integrated even when providers are unavailable. No fake external success is displayed. Known limitations are documented clearly. The result is suitable for a client demonstration, without claiming full production certification. 3. Non-Negotiable Rules Evidence beats assumptions. A page existing is not the same as the capability being operational. A local test is not hosted proof. A build pass is not production certification. Missing provider credentials are integration blockers, not permission to fabricate success. Never paste secrets into chat, source code, documentation or logs. Never weaken authentication, authorization, RLS/FORCE RLS, SSRF, rate limits, webhook validation or tenant boundaries to pass a test. Never use production credentials in local/E2E environments. Never use another customer's credentials. Never call WebRTC browser-to-browser E2E certified without the required realtime/browser-media infrastructure. Never call CCTV operationally proven without the real stream/recording/storage/worker chain. Never call DR proven without a restore drill. Never call enterprise scale proven from historical load tests alone. Customer credentials should activate infrastructure, not rescue unfinished core product. Keep every customer's credentials isolated to that customer's deployment. Inspect git diff and status before release. Classify evidence explicitly as PASS / FAIL / BLOCKED / DEFERRED / NOT TESTED / CODE VERIFIED ONLY / UNVALIDATED where appropriate. 19. Current Project Context Repository: Arunesh2004/CRM-v01. Final Direction The immediate mission is deliberately narrow: get the CRM into a trustworthy hosted state where a client can experience the Admin and Employee workflows as a coherent product. Core pages and actions should be present, connected and synchronized. Core CRM functionality should work without waiting for optional provider credentials. Provider-dependent functionality should be visibly present but honestly marked unavailable/degraded/demo when its required infrastructure is absent. Security and authorization must not be compromised to achieve the demo. After that milestone is proven on the hosted deployment, the client can provide their legitimate provider credentials/API configuration. Those credentials should be installed only into the intended isolated customer deployment/secret stores, then each provider can be activated and E2E-verified without rewriting the CRM's core business logic. Everything else remains important—but it comes later. The correct sequence is not 'finish every possible infrastructure dependency before showing anything.' It is 'finish and prove the product that can be proven now, demonstrate it honestly, then activate and certify the infrastructure that genuinely requires the client.'
