TESTING CONDITIONS AI Security + Business CRM Platform Admin → Employee → Full Workflow → Security → Communication → Credential Readiness Purpose: a complete evidence-first testing specification for the CRM before customer credentials are requested. It defines what must be tested, how it must be tested, how positive and negative paths are handled, and what evidence is required. It is not a declaration that every capability is currently implemented or production-certified. 1. Governing Principles Evidence beats assumptions: code existence is not runtime proof. Test the real hosted deployment for hosted claims; distinguish code-only, automated-test, hosted, authenticated-E2E, provider-E2E and production-certified evidence. Never weaken authentication, authorization, RLS/FORCE RLS, SSRF, rate limits, webhook validation or tenant boundaries to make a test pass. Never invent provider success. Missing credentials must result in explicit demo/test behavior or safe degradation according to capability criticality. Never paste passwords, API keys, database URLs, cookies, tokens or private secrets into chat, source control, reports or logs. Use synthetic/demo data. Never alter real customer data during testing. Every PASS requires reproducible evidence. Use PASS / FAIL / BLOCKED / DEFERRED / NOT APPLICABLE. Test happy paths AND unauthorized, malformed, duplicate, stale, timeout, retry and provider-failure paths. Do not call implementation maturity production certification. The project explicitly keeps these separate. fileciteturn284file0 2. Architectural Context The current target architecture is one codebase with a separately provisioned deployment/environment/infrastructure/credential set per company. Deployment isolation is the outer boundary; tenant isolation, application authorization and PostgreSQL RLS remain security boundaries inside a deployment. External vendors belong behind provider contracts/adapters, so customer credentials should configure the deployment rather than require a rewrite of CRM business logic. fileciteturn284file4 The testing program must therefore prove both the product itself and the ability to operate it safely when optional providers are missing. The current roadmap specifically identifies provider E2E, realtime/browser E2E, CCTV infrastructure, AI provider behavior, chaos/data-loss testing, DR, scale, provisioning and final certification as evidence areas that cannot be replaced by source inspection. fileciteturn284file2 3. Non-Negotiable Negative Tests Unknown user → DENY. Inactive user → DENY. Employee → Admin-only action → DENY. Tenant A → Tenant B resource → DENY. Forged tenantId → IGNORE/DENY. Forged resource owner → DENY. Invalid webhook signature → DENY. Replay webhook → reject/suppress. Duplicate event → idempotent. AI prompt injection → authorization unchanged. Unauthorized attachment/download → DENY. Expired session → DENY. Logout → protected operation no longer succeeds. 36. What Must Never Be Claimed Do not call a code-only feature E2E verified. Do not call a local test production-certified. Do not call a missing-provider capability operational. Do not call physical two-deployment isolation proven without an actual A/B test. Do not call DR proven without a restore drill. Do not call WebRTC browser-to-browser E2E proven without the required dual-user/browser/media infrastructure. Do not call AI production inference proven when the real provider was not exercised. Do not call CCTV operationally proven without the real stream/recording/storage/worker chain. Do not call enterprise scale proven from historical load tests alone. Do not request customer credentials to hide an unfinished core product. 37.
