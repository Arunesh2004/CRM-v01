            TESTING CONDITIONS            AI Security + Business CRM Platform            Admin → Employee → Full Workflow → Security → Communication → Credential Readiness      Purpose: a complete evidence-first testing specification for the CRM before customer credentials are requested.
It defines what must be tested, how it must be tested, how positive and negative paths are handled, and what evidence is required.
It is not a declaration that every capability is currently implemented or production-certified.
        1.
Governing Principles         Evidence beats assumptions: code existence is not runtime proof.
        Test the real hosted deployment for hosted claims; distinguish code-only, automated-test, hosted, authenticated-E2E, provider-E2E and production-certified evidence.
        Never weaken authentication, authorization, RLS/FORCE RLS, SSRF, rate limits, webhook validation or tenant boundaries to make a test pass.
        Never invent provider success.
Missing credentials must result in explicit demo/test behavior or safe degradation according to capability criticality.
        Never paste passwords, API keys, database URLs, cookies, tokens or private secrets into chat, source control, reports or logs.
        Use synthetic/demo data.
Never alter real customer data during testing.
        Every PASS requires reproducible evidence.
Use PASS / FAIL / BLOCKED / DEFERRED / NOT APPLICABLE.
        Test happy paths AND unauthorized, malformed, duplicate, stale, timeout, retry and provider-failure paths.
        Do not call implementation maturity production certification.
The project explicitly keeps these separate.

Architectural Context      The current target architecture is one codebase with a separately provisioned deployment/environment/infrastructure/credential set per company.
Deployment isolation is the outer boundary; tenant isolation, application authorization and PostgreSQL RLS remain security boundaries inside a deployment.
External vendors belong behind provider contracts/adapters, so customer credentials should configure the deployment rather than require a rewrite of CRM business logic.
fileciteturn284file4      The testing program must therefore prove both the product itself and the ability to operate it safely when optional providers are missing.
The current roadmap specifically identifies provider E2E, realtime/browser E2E, CCTV infrastructure, AI provider behavior, chaos/data-loss testing, DR, scale, provisioning and final certification as evidence areas that cannot be replaced by source inspection.

         GOAL             Architecture, Product Completion, Provider Agnosticism &amp; Final Certification            CRM — AI Security + Business CRM SaaS                       Executive Goal     Build the CRM as a strong, provider-agnostic platform whose core business, security, tenant, authorization, workflow and product logic does not need to be rewritten when a real client brings different external infrastructure.
Client-specific credentials and configuration should plug into explicit, secure provider contracts/adapters.
The platform must then be health-checked, integration-certified and made operational without redesigning the core product.
            1.
Purpose of This Goal      This document establishes a permanent product and architecture goal for the CRM project.
The objective is not merely to finish screens, APIs, or individual integrations.
The objective is to build a durable platform core that remains stable while external vendors and client infrastructure vary.
   The central architectural boundary is between the CRM's own business/security/domain logic and external systems such as email, telephony, realtime transport, storage, AI providers, CCTV streaming infrastructure, and related services.
External systems must be integrated through controlled boundaries rather than becoming embedded throughout the product.
   The project must therefore be evaluated on two separate dimensions: implementation maturity and real-world certification maturity.
A missing external credential is not automatically a missing application feature; similarly, an abstraction in source code is not proof that an arbitrary future provider will work.
        2.
Current Product Maturity      The current planning estimate is approximately 65–70% of the final product, with a best single-number estimate of about 67%.
This is a directional planning estimate, not a measured KPI, code-coverage figure, or contractual readiness score.
                    Dimension           Estimate           What it measures             Core engineering/platform foundation           ~80–85%           Architecture, security boundaries, abstractions, core infrastructure and substantial backend foundations.
            Application/product functionality           ~65–70%           Implemented product capability across CRM, communication, realtime, CCTV, AI, workforce, reporting and operations.
            Fully production-certified product           ~35–45%           Real-provider E2E, operational drills, scale evidence, client provisioning and final production certification.
        The lower production-certification percentage must not be interpreted as “only 35–45% of the product has been built.” Much of that gap consists of evidence that cannot honestly be generated until isolated, client-like infrastructure and legitimate credentials are available.

The Core Requirement: Credentials Should Configure, Not Rebuild      The fundamental requirement is that when a real client supplies legitimate credentials, endpoints, identifiers and supported infrastructure, the deployment should become operational primarily through configuration and certification—not by rewriting the CRM's core business logic.
            Client infrastructure           ↓   credentials + configuration           ↓   provider contract / adapter           ↓   health checks + capability detection           ↓   sandbox / integration certification           ↓   READY      This means provider-specific implementation belongs at the boundary.
The CRM core should own business meaning, authorization, tenant isolation, lifecycle, auditability, workflows and domain rules.
The external adapter should translate those requirements into the provider's API/protocol semantics.
        5.
What “Regardless of the Platform” Means      “Regardless of the platform” should be treated as provider/platform independence, not as a literal promise that every arbitrary vendor on earth will work with one credential field and zero integration effort.
External platforms can expose fundamentally different APIs, protocols, authentication models, webhook systems and capabilities.
                      Correct interpretation     For every supported integration class, the CRM core remains stable and external systems are connected through explicit provider contracts/adapters.

         How to handle credentials            AI Security + Business CRM SaaS   Credential, provider, deployment, demo-mode, and buyer-provisioning policy         1.
Purpose      This is the operating policy for credentials across development, testing, Production, and future buyer deployments.
It explains what must be real, what may safely degrade, how secrets are stored, and how buyer-specific infrastructure is configured.
        2.
Fundamental architecture      The CRM is intended to use isolated deployments per company/customer.
Credentials belong to the deployment they serve and must never be shared between customers.
        Current deployment: use the real credentials already legitimately configured for it.
        Optional provider missing: keep the CRM usable through safe disabled/degraded behavior where supported.
        Buyer purchase: create an isolated client deployment and configure that client's own credentials.
        Provider portability is required, but a different provider works only when an existing adapter/interface and runtime support it; otherwise a new adapter/integration is required.
        3.
Core vs optional credentials      Core security infrastructure must remain real: database, authentication, authorization/RBAC, tenant isolation/RLS, encryption/signing, audit integrity, and other security-critical dependencies.
     Optional credentials may cover email, SMS/voice, WhatsApp, AI, CCTV, storage, realtime, background jobs, and other integrations.
Their absence must not unnecessarily crash the core CRM.
        4.
Missing credentials: correct behavior      If an optional credential is absent, the system should use an explicit unavailable/degraded state or an existing safe demo workflow.
It must never pretend an external operation succeeded.
        Good: “Email provider not configured.”         Good: “Demo mode — no external message was sent.”         Bad: “Email sent successfully” when no email was sent.
        Bad: fake provider message IDs, fake delivery timestamps, or fake delivery records.

        Never add random demo credentials to Production just to make a feature appear configured.
        Never use another customer's credentials.
        Never use developer credentials as a hidden Production fallback.
        Never silently fall back from one provider to another.
        6.

        Prefer read-only health/configuration checks.
        Do not send test email/SMS/WhatsApp or make calls from Production unless explicitly authorized and using a known-safe test resource.
        Do not seed fake data into Production unless an approved dedicated demo-tenant procedure exists.
        Do not change Production credentials merely to make certification pass.
        15.
Failure semantics      Missing configuration must be distinguishable from provider outage, authentication failure, rate limiting, and other runtime failures.
Optional-provider failures should affect the specific operation/feature, not unrelated CRM functionality.
A missing provider must never become a fake success.
        16.
Quick decision tree         Credential present? → use the configured real provider.
        Credential absent? → Is it CORE? If yes, fail/block safely.
        Optional? → Is safe degraded/demo behavior available? If yes, use it.
        No safe fallback? → disable the affected feature and report provider not configured.
        Buyer arrives? → provision an isolated deployment and configure the buyer's credentials there.
        Buyer chooses a new provider? → check adapter support; add and validate an adapter only when required.
        17.
Non-negotiable rules         Core security credentials are always real.
        No fake credentials.
        No secret values in chat or documentation.
        No cross-customer credential sharing.
        No hidden fallback to Production credentials.
        No fake success for external operations.
        Optional providers must not unnecessarily prevent the core CRM from running.
        Buyer credentials belong only to the buyer's isolated deployment.
        Provider portability must be based on actual adapter/runtime compatibility.
        Certification must never weaken security.
        18.
Final operating principle         Use what we legitimately have today.
Safely degrade what we do not have.
When a buyer arrives, configure that buyer's own infrastructure and credentials in that buyer's isolated deployment.
