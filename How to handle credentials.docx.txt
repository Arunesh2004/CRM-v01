How to handle credentials AI Security + Business CRM SaaS Credential, provider, deployment, demo-mode, and buyer-provisioning policy 1. Purpose This is the operating policy for credentials across development, testing, Production, and future buyer deployments. It explains what must be real, what may safely degrade, how secrets are stored, and how buyer-specific infrastructure is configured. 2. Fundamental architecture The CRM is intended to use isolated deployments per company/customer. Credentials belong to the deployment they serve and must never be shared between customers. Current deployment: use the real credentials already legitimately configured for it. Optional provider missing: keep the CRM usable through safe disabled/degraded behavior where supported. Buyer purchase: create an isolated client deployment and configure that client's own credentials. Provider portability is required, but a different provider works only when an existing adapter/interface and runtime support it; otherwise a new adapter/integration is required. 3. Core vs optional credentials Core security infrastructure must remain real: database, authentication, authorization/RBAC, tenant isolation/RLS, encryption/signing, audit integrity, and other security-critical dependencies. Optional credentials may cover email, SMS/voice, WhatsApp, AI, CCTV, storage, realtime, background jobs, and other integrations. Their absence must not unnecessarily crash the core CRM. 4. Missing credentials: correct behavior If an optional credential is absent, the system should use an explicit unavailable/degraded state or an existing safe demo workflow. It must never pretend an external operation succeeded. Good: “Email provider not configured.” Good: “Demo mode — no external message was sent.” Bad: “Email sent successfully” when no email was sent. Bad: fake provider message IDs, fake delivery timestamps, or fake delivery records. 5. Never use fake credentials Never invent API keys, passwords, database URLs, tokens, webhook secrets, signing keys, or encryption keys. Never add random demo credentials to Production just to make a feature appear configured. Never use another customer's credentials. Never use developer credentials as a hidden Production fallback. Never silently fall back from one provider to another. 6. Current project credential model Credentials already obtained for the current project are stored in the appropriate Vercel environment/secret store. Secret values must never be printed in chat, reports, source control, screenshots, or temporary files. Configuration inventories should contain only metadata such as CONFIGURED, NOT CONFIGURED, UNKNOWN, or DEFERRED. 7. Environment separation Local/E2E credentials → local test infrastructure only. Preview/Staging credentials → isolated non-Production resources only. Production credentials → Production only. Client credentials → that client's isolated deployment only. Never copy Production credentials into local, staging, preview, demo, or test environments. Never copy one client's credentials into another client's deployment. 8. A buyer's alternative provider requires an existing adapter or a future adapter. 9. Provider portability SUPPORTED NOW → configure it for the client. SUPPORTED THROUGH EXISTING INTERFACE → use the compatible implementation. NO ADAPTER → implement and validate an adapter before claiming support. UNSUPPORTED → credentials alone do not make it work. 10. Infrastructure portability A buyer may choose different infrastructure, but compatibility must be verified rather than assumed. AWS instead of Supabase: potentially suitable when the target supplies the PostgreSQL/extensions/features the application actually requires. Another PostgreSQL host: not automatically equivalent if provider-specific services are required. Hostinger instead of Vercel: requires verification of Next.js/Node runtime, workers, cron/background jobs, realtime, storage, and other dependencies. Credentials cannot replace infrastructure components the software genuinely needs. 11. Buyer provisioning model Create the buyer's isolated deployment/environment. Provision or connect the buyer's database/infrastructure. Configure authentication and encryption/security settings. Configure providers selected by the buyer. Store secrets in that client's deployment secret store. Validate configuration without exposing secret values. Enable only integrations whose prerequisites are configured. Run client-specific security/integration/production certification. Freeze the certified environment. 12. Replacing current providers for a buyer The current project's credentials are not the buyer's credentials. A buyer's isolated deployment receives client-specific values. If the buyer selects a different supported provider, configure its adapter. If no adapter exists, implement one during the appropriate engineering phase before claiming support. Never overwrite one deployment's credentials to configure another customer. 13. Secret handling rules Do not ask users to paste secrets into chat when a secure secret-management path exists. Never print secret values in terminal output, logs, reports, screenshots, or documentation. Never commit secrets to Git. Never create .env.production.local with real Production credentials for temporary testing. Do not pull secrets locally merely to prove presence when safe metadata can establish it. If a secret is exposed, treat it as compromised and rotate it through the provider/Vercel secret-management workflow. 14. Production testing Production is not a sandbox. Prefer read-only health/configuration checks. Do not send test email/SMS/WhatsApp or make calls from Production unless explicitly authorized and using a known-safe test resource. Do not seed fake data into Production unless an approved dedicated demo-tenant procedure exists. Do not change Production credentials merely to make certification pass. 15. Failure semantics Missing configuration must be distinguishable from provider outage, authentication failure, rate limiting, and other runtime failures. Optional-provider failures should affect the specific operation/feature, not unrelated CRM functionality. A missing provider must never become a fake success. 16. Quick decision tree Credential present? → use the configured real provider. Credential absent? → Is it CORE? If yes, fail/block safely. Optional? → Is safe degraded/demo behavior available? If yes, use it. No safe fallback? → disable the affected feature and report provider not configured. Buyer arrives? → provision an isolated deployment and configure the buyer's credentials there. Buyer chooses a new provider? → check adapter support; add and validate an adapter only when required. 17. Non-negotiable rules Core security credentials are always real. No fake credentials. No secret values in chat or documentation. No cross-customer credential sharing. No hidden fallback to Production credentials. No fake success for external operations. Optional providers must not unnecessarily prevent the core CRM from running. Buyer credentials belong only to the buyer's isolated deployment. Provider portability must be based on actual adapter/runtime compatibility. Certification must never weaken security. 18. Final operating principle Use what we legitimately have today. Safely degrade what we do not have. When a buyer arrives, configure that buyer's own infrastructure and credentials in that buyer's isolated deployment.
